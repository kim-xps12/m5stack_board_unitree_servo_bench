# DYNAMIXEL TTL 基板の改良・再設計 — 調査・考察・修正方針

- 対象: M5Stack AtomS3R ↔ 自作 DYNAMIXEL TTL 基板 ([kim-xps12/m5stack_board_dynamixel_ttl_rs3485](https://github.com/kim-xps12/m5stack_board_dynamixel_ttl_rs3485)) ↔ Unitree S288 (ID 0)
- 作成: 2026-10-11
- 測定: `atoms3r/tools/bench.py`、`atoms3r/tools/first_edge.py` (ログは `atoms3r/logs/`。git 管理外)
- 解説 (用語の定義、修正案と各社の回路の比較): [s288_link_explained.md](s288_link_explained.md)

## 要約

- **4 Mbps で通らない原因は「送信開始の最初の立下りの遅れ S」です。** 現行基板はトランジスタで DE を作っているので、最初の Low (スタートビット) が S だけ短くなります。R2 に 220 pF を足したことで S が 50 ns から 88 ns に増え、サーボの許容範囲を超えました。
- **実機で直接確かめました。** パケットの最初の Low だけを 62.5〜175 ns 伸ばして S を打ち消すと、4 Mbps ちょうどで停止コマンドもランダムなコマンドも 100% 通ります。そのときの受信窓 (100% の範囲 −2.1〜+1.2%) は公式アダプタ (−2.44〜+0.63%) と同等以上です。
- **新たに分かったサーボの性質が 2 つあります。**
  - **フレームの区切り**: 1 ビット (250 ns) の空きでもフレームの区切りとみなします。パケットは途切れなく送る必要があり、パケットの直前にゴミバイトが連続していても失敗します。
  - **応答の開始**: 応答は、こちらのパケットが終わってから約 21 µs 後に始まります。mode 0 と mode 1 で差はありません。
- **修正方針**: OpenRB-150 の「TTL with Auto TX Enable」回路 (ダイオード + RC + Schmitt インバータ + LVC 3-state バッファ) をベースに、ロジックをすべて 3.3 V にして定数を見直します。設計目標は次のとおりです。
  - S ≤ 20 ns (遅れが出るのは先頭の 1 回だけ)
  - DE 保持 ≥ 3.2 µs
  - DE 解放 ≤ 7.3 µs
- **暫定策** (現行基板に 220 pF を付けたまま): パケットの先頭に 0xFF を 1 バイト足すと、4 Mbps で 600/600 通ります。ただし S が大きいことに依存した偶然の効果なので、新基板には使えません (§8)。
- **優先順位** (同日追記): 基板を作り直す前に、現行基板 (220 pF 付き) のまま、送信を RMT にして最初の Low を約 120 ns 伸ばす方法 (解説文書 §4 の案 C) を試します。これで十分なら、作り直しは AtomS3R 以外から使いたくなるまで保留します。この文書の再設計方針は、そのときの計画として残します。

## 1. 対象システムと現行回路

### 1.1 リンクの仕様

| 項目 | 値 |
|---|---|
| 物理層 | 1 本線の半二重、ノンインバート UART (8N1) |
| ボーレート | 4 Mbps (1 bit = 250 ns)。サーボ自身の送信は 3.996 Mbps (−0.09%) と実測 |
| コマンド | 20 バイト (`FE EE` … CRC32) = 50 µs |
| 応答 | 26 バイト (`FC EE` …) |
| パケット内で最も長い High の連続 | 9 bit = 2.25 µs (0xFF のデータ 8 bit + ストップ) |
| MCU | ESP32-S3 (AtomS3R)。I/O は 3.3 V で、**5 V トレラントではない** |
| 接続 | Grove: G2 = TX、G1 = RX、5 V、GND (空きピンはない) |

### 1.2 現行基板

```
STS_TX ──R1 7.5k──┤B  Q1 2SA1162 (PNP, E = 3.3V)
                     C ──┬── DE / /RE (MAX3485, 3.3V)
                         R2 20k (+ 220pF を後付け)
                         GND
STS_TX ── DI   A ── 信号線 (R5 10k で 3.3V へプルアップ)
STS_RX ── RO   B ── 1.65V (R3/R4 2.2k で分圧)
```

- TXD が Low になると Q1 がオンし、DE = High で送信します。RO は Hi-Z になります。
- TXD が High に戻ると Q1 はオフになりますが、蓄積時間と R2 による放電の分だけ DE が残ります (保持)。
- MAX3485 は差動ではなく、A を信号、B を固定バイアスとする片側駆動で使っています。

### 1.3 自動方向切替に必要な 3 つの時間

```
TXD     ‾‾‾‾\______/‾‾‾\___ … ___/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
DE      ____/‾‾‾‾‾‾‾‾‾‾‾‾‾‾ … ‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\_____________________
バス     ‾‾‾‾‾‾‾\___/‾‾‾\___ … ___/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\__/‾\_ (応答)
            |←S→|                  |← DE 解放 →|← ≈17 µs →|
```

| 時間 | 意味 | 長すぎた場合 / 短すぎた場合 |
|---|---|---|
| **S** (イネーブル遅れ) | TXD の立下りからバスに Low が出るまでの、データ経路に対する遅れ | スタートビットが S だけ短くなる。DE が落ちていれば再イネーブルのたびに発生する |
| **保持** | TXD が High の間、DE を出し続ける時間 | 9 bit (2.25 µs) より短いと、パケットの途中で DE が落ちる (再イネーブル) |
| **解放** | 最後の立上りから DE が落ちるまで | サーボの応答開始より遅いと、応答とぶつかる |

## 3. 現行基板の測定結果

### 3.1 タイミング (ベンチでの測定、サーボなし)

| 状態 | S (先頭の立下り) | DE 解放 | パケット途中の再イネーブル |
|---|---|---|---|
| 午前 (R2 = 20 kΩ のみ) | 50 ns | 0.8〜1.5 µs (データ依存。Q1 の蓄積時間) | あり (保持 < 9 bit) |
| 午後 (R2 ∥ 220 pF) | 88 ns | 3.8〜6 µs (τ = 20 kΩ × 220 pF = 4.4 µs) | なし |

S の内訳は「Q1 が DE ノードを充電する時間 (220 pF なしで 5〜20 ns、ありで 40〜55 ns)」と「MAX3485 の (tPZL − 伝搬遅延)」です。後者は 2 点から当てはめると約 30〜45 ns で、これが S の下限になります (MAX3485 の tPZL は typ 45 / max 90 ns)。**つまり Q1 をいくら速くしても、MAX3485 を使う限り S は 30〜45 ns を下回りません。**

### 3.2 受信窓 (サーボ応答率 100% となるボーレートのずれ)

| 構成 | コマンド | 100% の範囲 | 備考 |
|---|---|---|---|
| 公式 Unitree アダプタ | 停止 | −2.44〜+0.63% | +0.95〜+2.56% は 94〜97% |
| 現行基板・午前 | 停止 | −3.03〜+0.31% | |
| 現行基板・午前 | ランダム (mode 1) | −1.23% のみ | 4 Mbps では 37%。データ依存 |
| 現行基板・午後 (220 pF) | 停止 | なし | 3.878〜3.902 Mbps で約 90% が最大、4 Mbps で 0% |

`sin_swing` (振幅 0.5 rad、200 Hz) で応答を取りこぼした割合 (午前): 4 Mbps で約 51%、3.950617 Mbps (−1.23%) で 0.08〜0.4%。

### 3.3 解釈

- **午前のデータ依存**: 温度ではなく、パケット途中の DE 再イネーブルが原因でした。保持 (0.8〜1.5 µs) が High の連続 (最長 2.25 µs) より短いので、データ次第でパケットの途中で DE が落ち、次の立下りが S だけ遅れます。§4.3 で裏付けています。
- **220 pF の影響**: 再イネーブルはなくなりましたが、先頭の S が 88 ns に増え、サーボが受け付ける限界を超えました。

## 4. 再設計前の実機検証 (2026-10-11 夜、220 pF 付きの基板)

### 4.1 方法

`first_edge.py` の GEN 合成で、UART を使わずに送信しました。条件はどれも、停止コマンドとランダムな mode 1 コマンド (ゲインとトルク 0) の両方で、1 点あたり 40〜600 回です。

- **E0 (手法の妥当性)**: D = 0 で UART と GEN の結果が一致することを確認しました。4 Mbps では UART 0/50、GEN 0/50。−2.74% では UART 43/50、GEN 44/50 です。

### 4.2 E1: 先頭補償 D の掃引 (4 Mbps ちょうど)

| D | 停止 | ランダム |
|---|---|---|
| ≤ 37.5 ns (0〜3 tick) | 0% | 0% |
| 50 ns (4) | 60〜98% | 60〜95% |
| **62.5〜175 ns (5〜14)** | **100%** | **100%** |
| 187.5 ns (15) | 72〜100% | 78〜80% |
| ≥ 200 ns (16〜) | 0% | 0% |

(同じ掃引を 2 回行いました: n = 40 と n = 10)

- **補償の効果**: S を 62.5 ns 以上打ち消せば、4 Mbps ちょうどで通ります。**原因が先頭の立下りの遅れであることが直接確かめられました。**
- **ベンチの S (88 ns) に換算した場合**:
  - 実効的な先頭の遅れ S_eff = S − D が **+25 ns 以下なら 100%**、+38 ns で一部失敗、**+50 ns 以上で 0%** です。
  - スタートビットを長くする方向 (S_eff < 0) には −87 ns まで耐えます。
- **残る不整合**: 午前の基板は S = 50 ns でも、停止コマンドなら 4 Mbps で通っていました。この点は上の換算と 10〜20 ns 食い違います。サーボをつないだ状態の S は、ベンチで測った値から多少ずれると考えられます。
- **設計目標**: S ≤ 20 ns とします (限界は 25〜50 ns)。

### 4.3 E2: S を打ち消したときの受信窓 (D = 125 ns)

| ずれ | 停止 | ランダム |
|---|---|---|
| ≤ −2.7% | 0% | 0〜10% |
| −2.4% | 78〜100% | 78〜100% |
| **−2.1〜+1.2%** | **100%** | **100%** |
| +1.5% | 80〜100% | 100% |
| ≥ +1.8% | 0% | 0% |

- **データ依存の消失**: パケットの間ずっと DE を保持し、先頭の遅れを打ち消すと、停止コマンドとランダムなコマンドの差は**完全になくなります**。午前のデータ依存の原因が再イネーブルだったことの裏付けです。
- **公式アダプタとの比較**: 100% の範囲は 2 回の測定とも −2.1〜+1.2% (幅 3.3%) で、公式アダプタ (幅 3.1%) と同等以上です。

### 4.4 E3: サーボが応答を始めるまでの時間

| コマンド | DE 解放 → 応答開始 (µs)。min / 中央値 / max | n |
|---|---|---|
| 停止 (mode 0) | 16.95 / 17.09 / 18.43 | 1144 |
| ランダム (mode 1) | 16.51 / 17.02 / 20.14 | 1100 |

この基板では DE が最後の立上りの 3.8〜6 µs 後に解放されます。そのため、こちらのパケットが終わってから応答が始まるまでは **約 21 µs (20 µs 以上)** です。午前の基板 (解放 0.8〜1.5 µs、解放 → 応答 20.1 µs) とも合います。mode 1 でも短くならないことが分かりました。**DE は 10 µs 以内に解放すれば十分です。**

### 4.5 E4/E5: フレームの区切り

| 送り方 (4 Mbps) | 結果 |
|---|---|
| 先頭バイトなし (D = 0) | 0% |
| `00` + パケット、間を空けずに (D = 0) | 0% (n = 80) |
| `FF` + パケット、間を空けずに (D = 0) | **100% (600/600)** |
| `00` / `FF` / `55` + パケット、間を空けずに、先頭バイトを補償 (D = 62.5〜125 ns) | **0% (全 1800 回)** |
| `00` + 1 bit の空き + パケット (D = 100 ns) | 100% (n = 120) |
| `00` + 1 µs / 3 µs の空き + パケット (D = 0) | 100% (各 600/600) |
| パケットの途中に 1 bit の空き (位置は問わず。D = 125 ns) | **0%** |
| パケットの途中に 4 bit / 12 bit の空き | 0% |

- **フレームの区切り方**: サーボは **1 ビットの空きでもフレームの区切り**とみなし、フレームがヘッダから始まらなければ捨てます。パケットの途中に空きを入れることも、直前にゴミバイトを続けることもできません。
- **`FF` 連続が通る理由**: S によって 0xFF のスタートビットが約 160 ns に縮み、サーボがそれをバイトとして拾わないためです。同じ 0xFF でも補償してきちんと受信させると 0% になるので、これは確かです。
- **`00` 連続が通らない理由**: 0x00 は Low が 9 bit 続くので、遅れがあっても 1 バイトとして受信され、ヘッダの前のゴミになります。

### 4.6 サーボ受信器のモデル (推定)

E1 と E2 の両方を説明できるのは、次のモデルです。

- サーボは理想的な位置 (ビットの中央) より **約 30 ns 遅れて** サンプリングし、そこから **±約 70 ns** までずれても受信できる。
- S のない 2 バイト目以降の + 側の限界: (74 − 30) ns ÷ (9.5 bit × 250 ns) ≈ +1.85% (実測 +1.5〜+1.8%)
- 先頭バイト (S_eff = −37 ns) の − 側の限界: (74 − 37 + 30) ns ÷ 2375 ns ≈ −2.8% (実測 −2.4〜−2.7%)
- 公式アダプタの窓の中心が −0.9% に寄っていること (≈ 21 ns の遅れに相当) とも合う。

**設計への示唆**: 理想的な基板 (S = 0) でも、遅れる側の余裕は約 40 ns しかありません。先頭の S はその余裕を直接削るので、小さいほど良いことになります。

### 4.7 設計要求のまとめ

| 要求 | 値 | 根拠 |
|---|---|---|
| 先頭の立下りの遅れ S | **≤ 20 ns** (限界 25〜50 ns) | E1 |
| 2 回目以降の立下りの遅れ | 0 (パケット中に DE を落とさない) | E2、§3.3 |
| DE 保持の最小値 | > 2.25 µs (9 bit) | プロトコル |
| DE 解放の最大値 | ≤ 10 µs (応答開始 ≈ 21 µs) | E3 |
| パケット内の空き | 0 bit | E5 |
| バスの High レベル | 3.3 V で駆動した実績あり (現行の MAX3485) | §3 |
| RX 出力のレベル | 3.3 V 以下 (ESP32-S3 保護のため) | |

## 5. 候補回路の比較

| 回路 | S | High の出し方 | DE 保持 / 解放 | AtomS3R との相性 | 評価 |
|---|---|---|---|---|---|
| 現行 (PNP + MAX3485) | 50 / 88 ns (実測) | 能動駆動 | 0.8〜1.5 µs、データ依存 / 3.8〜6 µs | ○ | MAX3485 による 30〜45 ns の下限が残る |
| Feetech (PNP + LVC126/125) | 推定 5〜20 ns。再イネーブルのたびに発生 | 能動駆動 (解放後は 10 kΩ) | 0.5〜1.5 µs、データ依存 | ○ | 下限は消えるが、保持がデータに依存して短い。1 Mbps 向けの設計 |
| **OpenRB-150** (ダイオード RC + Schmitt + LVC) | 推定 10〜25 ns。先頭の 1 回だけ | 能動駆動 | τ = 7 µs。5 V の HC では解放が 10 µs〜解放されない | △ (3.3 V 入力に対して閾値と VIH が合わない) | **作りは最良。定数と電源電圧を直せばよい** |
| TTLinker_mini (HC126 + インバータ) | 推定 5〜10 ns。全ての立下りで発生 | **受動** (1 kΩ プルアップ) | 保持なし | × (5 V の HC。RXD に 5 V が出る) | 立上りがケーブル次第。そのままでは接続不可 |
| dir ピン (ファームで制御) | ≈ 0 | 能動駆動 | ファームで決まる | △ (Grove に空きピンがない) | 線が 1 本増える。§6.5 のオプションとして残す |

OpenRB-150 の原回路について、補足が 2 点あります。

- **U4 (74HC2G14)**: 5 V 動作の HC2G14 を 3.3 V の TXD で駆動しています。HC2G14 の VT+ は 5 V で約 2.5〜3.5 V なので、解放は 10〜15 µs になり、最悪の場合は解放されません。DYNAMIXEL の Return Delay Time は既定で 500 µs なので問題になりませんが、S288 (応答開始 ≈ 21 µs) では衝突の危険があります。
- **U3 (74LVC1G126)**: 5 V 動作なので、3.3 V 入力では VIH (0.7 × VCC = 3.5 V) を満たしません。

## 6. 修正方針: OpenRB-150 回路の 3.3 V 化

### 6.1 回路

```
                       +3.3V
                         │
STS_TX (G2) ──┬──────────┼──────────────────────────► A
              │          │                              U3 74LVC1G126 (3.3V)
              │   D1 ショットキー (A = RC ノード, K = STS_TX)        Y ──┬── R20 47Ω ── 信号線 (J3/J4 pin 3)
              ├───┤◄├───┐                         ┌────► OE    │
              │         │                         │            ├── R21 10k ── +3.3V
              └─ R16 ───┴── RC ──► U4 74LVC1G14 ──┼── TXEN     │
                 68k 1% │          (3.3V, 反転)    │            │
                     C16 100pF                 R19 10k         └──► A  U7 74LVC1G125 (3.3V)  Y ──► STS_RX (G1)
                     C0G 5%                       │      TXEN ───► /OE
                        │                        GND
                       GND
(オプション) RC ──┤◄├── DIR_N パッド (D2、未実装)
(オプション) 信号線 ── TP_BUS (G5 プローブ用)
+3.3V ── R_bleed 470 ── GND (§6.4。当初 2.2k)
```

動作は次のとおりです。

1. TXD が Low になると、D1 が RC ノードを即座に引き下げます。U4 の出力 TXEN が High になり、U3 が送信し、U7 は Hi-Z になります。
2. TXD が High の間は、R16 × C16 でゆっくり充電されます。VT+ を超えると TXEN が Low に戻り、受信に切り替わります。
3. Low が来るたびに RC ノードがリセットされるので、**DE はパケットの間ずっと保持され、遅れ S が出るのは先頭の立下りだけ**です。

### 6.2 部品と OpenRB-150 からの変更点

| 記号 | 部品 | 電源 | OpenRB-150 の対応部品 | 変更の理由 |
|---|---|---|---|---|
| U4 | 74LVC1G14 (SOT-353) | 3.3 V | U4 74HC2G14 (5 V) | 3.3 V の TXD に合った閾値 (VT+ 1.50〜2.00 V)。解放時間を決められる |
| U3 | 74LVC1G126 | **3.3 V** | U3 74LVC1G126 (5 V) | VIH 違反を解消。バスを 3.3 V で駆動 (現行基板と同じ実績のあるレベル) |
| U7 | 74LVC1G125 | 3.3 V | 同じ | 入力は 5.5 V トレラント (Ioff あり)。出力 3.3 V |
| D1 | 小信号ショットキー (RB751S40 / BAT54 など、低リーク品) | — | D2 BAS16 | Vf を 0.7 V から 0.3 V に下げ、VT− (最小 0.80 V) との余裕を確保 |
| R16 | 68 kΩ 1% | — | R16 47 kΩ | C16 を減らした分、τ をほぼ同じに保つ |

### 6.3 タイミング設計

**DE の解放 (= 保持) 時間**

t = τ · ln((V_OH − V0) / (V_OH − VT+))。各値は次のとおりです。

- τ = 68 kΩ × 100 pF = 6.8 µs (R 1%、C 5% で ±6%)
- V_OH = 3.3 V
- V0 = 0〜0.3 V (D1 の Vf の残り)
- VT+ = 1.50〜2.10 V (Diodes 製データシートの 3.0 V での値 1.50〜2.00 V を 3.3 V に補正)

| 条件 | τ | V0 | VT+ | t |
|---|---|---|---|---|
| 最短 | 6.39 µs | 0.3 V | 1.50 V | **3.27 µs** |
| 典型 | 6.8 µs | 0.1 V | 1.8 V | 5.2 µs |
| 最長 | 7.21 µs | 0 V | 2.10 V | **7.30 µs** |

- 最短 3.27 µs > 最長の High 連続 2.25 µs (余裕 1.45 倍) → パケット途中の再イネーブルは起きません。
- 最長 7.30 µs < 応答開始 ≈ 21 µs (余裕 13 µs 以上) → 応答と衝突しません。
- OpenRB の原定数 (47 kΩ ±5% / 150 pF ±10%) を同じ 3.3 V 回路に入れると、3.08〜8.24 µs です (余裕は 2.25 µs に対して 1.37 倍、解放の上限 10 µs に対して 1.21 倍。本設計は 1.45 倍 / 1.37 倍)。C が X7R なら温度でさらに ±15% 変わり、2.62〜9.47 µs (余裕 1.16 倍 / 1.06 倍) です。要求は満たしますが、余裕は小さくなります。(2026-10-12 訂正。以前は 68 kΩ / 100 pF と同じ許容差で計算した 3.4〜7.6 µs と書いていました)
- C16 を 150 pF のままにすると、S のうち TX ピンの立下りによる分が 1.7〜9.2 ns から 2.5〜13.6 ns に増え、最悪の S は約 20 ns と要求の上限に届きます。

**先頭の遅れ S の見積り**

| 要素 | 値 |
|---|---|
| TXD ピンの立下り (ESP32-S3 の出力抵抗 約 40〜80 Ω × 約 105 pF ≈ 4〜8 ns) | データ経路は U3 の閾値 (約 1.5 V) を 0.8τ で通過し、イネーブル経路は RC ノードが VT− (0.8〜1.3 V) に達するのに 1.2〜1.9τ かかる → 差は 2〜8 ns |
| U4 の tpd (3.3 V) | 0.7〜4.6 ns |
| U3 の (tPZL − tPHL) | 約 ±3 ns |
| **S の合計** | **典型 5〜10 ns、最悪 約 16 ns** (現行は 50 / 88 ns) |

ファーム側で TX ピンの駆動能力を最大 (`GPIO_DRIVE_CAP_3`) にすると、さらに短くなります。

### 6.4 電圧レベルと保護

- **AtomS3R 側の電圧**: STS_TX / STS_RX はどちらも 3.3 V 系です。U7 は 3.3 V 電源なので、バス側が 5 V になっても RX ピンに 5 V は出ません。
- **サーボ側の信号電圧は未確認です。** README の「サーボ接続時にバスが 0〜5 V で振れる」という記述は注意書きで、実測の根拠はありません。サーボだけに給電し、基板を外した状態で信号ピンの電圧をテスターで測ってください。
  - **≈ 3.3 V か浮いている場合**: 本設計 (全 3.3 V) のままで問題ありません。
  - **≈ 5 V の場合** (サーボが 5 V にプルアップしている): サーボ側のプルアップから R21 と U3 の出力を通って、3.3 V レールに電流が流れ込みます。U3 が High を出している間は (5 − 3.3) V ÷ サーボ側プルアップ抵抗で、たとえば 1 kΩ なら 1.7 mA です。LDO は電流を吸い込めず、LVC の消費電流は µA 級なので、レール電圧が上がる恐れがあります。R_bleed で吸収します。既定値 2.2 kΩ (1.5 mA) を、流れ込む電流の見積りより大きくなるように選び直してください。サーボ側のプルアップ抵抗は、アイドル時のバス電圧と R21 の分圧から求められます。
  - **結果 (2026-10-12、ユーザ確認)**: サーボの信号は 5 V 系でした。プルアップの値は分からないので、R_bleed を 470 Ω (7.0 mA) にしました。U3 が High を出している間に流れ込む電流は (5 − 3.3) V ÷ (サーボ側プルアップ ÷ 台数 + 47 Ω + U3 の出力抵抗 約 25 Ω) で、5 ポートすべてに 850 Ω 以上のプルアップがあれば 7.0 mA 以下に収まり、レールは持ち上がりません。常に 7 mA 余分に流れ、R_bleed の損失は 23 mW (0603 の定格 100 mW) です。試作基板で、5 台に送信している間の 3.3 V を測って確かめます。
- **バスを 5 V で駆動する変形案**: U3 を 5 V 電源の 74AHCT1G126 (VIH 2.0 V、tpd max 6.5 ns) にし、R21 を 5 V につなぐと、OpenRB と同じ 0〜5 V のバスになります。サーボが 5 V を許容すると確認できた場合の選択肢です。その場合の注意点は 2 つです。
  - AHCT には Ioff がなく、無給電時にバスから逆流します。
  - G5 プローブを直結できなくなるので、分圧が必要です。
- **LVC の 5.5 V 耐性**: U3 の出力、U7 の入力とも、Hi-Z 時と無給電時に 5.5 V まで耐えます (Ioff)。

### 6.5 オプション

- **DIR_N パッド (未実装)**: RC ノードから 2 本目のショットキー D2 を引き出し、AtomS3R 下面のピン (G5〜G8、G38、G39) につなぎます。GPIO を Low にすると TXEN が強制的に有効になります。
  - ESP-IDF の RS485 半二重モードでは RTS がハードウェアで制御されます。GPIO マトリクスでこれを反転出力すれば、ファームでの方向制御にあとから切り替えられます (解放はファームの解放時刻 + 3.3〜7.3 µs)。
- **TP_BUS**: G5 でベンチ測定するための信号線テストパッドです。全 3.3 V 構成なら、サーボを外した状態で直結できます。
- **フットプリントの互換**: U3 の SOT-353 は、74LVC1G126 と 74AHCT1G126 でピン配置が同じです。U3 の VCC と R21 の接続先を、はんだジャンパで 3.3 V / 5 V から選べるようにしておけば、§6.4 の変形案には部品の変更だけで切り替えられます。

### 6.6 ファームウェアの対応

- **ボーレート**: 4,000,000 bps ちょうどに戻します (80 MHz / 20)。新基板は 4 Mbps だけを扱い、サーボのボーレートは使う前にユーザが Unitree の公式ツールで 4 Mbps に設定します (2026-10-12 決定)。`sin_swing` の既定値 3,950,617 bps は、この基板の不具合を回避するためのものです。
- **一括書き込み**: 20 バイトのパケットは `uart_write_bytes` 1 回で FIFO に書き込み、途切れなく送ります (E5: 1 bit の空きでも失敗します)。
- **駆動能力**: TX ピンの駆動能力を最大にします。
- **応答待ち**: 応答はこちらのパケットが終わってから約 21 µs 後に始まります。DE は 7.3 µs 以内に解放されるので、追加の待ち時間は不要です。

  - **ピン番号**: メーカーと JLCPCB の番号は、ラッチを下にしたとき右端が 1 番で、旧フットプリントと逆です。銅箔の位置は変えず、番号だけを付け替えました。回路図では J2 を上下反転しただけで、配線は変えていません。新しい番号は 1 = GND、2 = +5V、3 = TX (G2)、4 = RX (G1) で、M5Stack の Grove の番号と同じです。旧番号のままだと、JLCPCB 側で 1 番ピンを合わせようとして 180° 回され、電源が逆接になる恐れがありました。
  - **TX / RX の並びの確認 (2026-10-12)**:
    - DYNAMIXEL 版 v2 (GitHub の master) と比べると、4 本のパッドの x 座標、ネット (左から STS_RX、STS_TX、+5V、GND)、シルク「Rx Tx V G」、ロック窓が基板の内側を向く向きが一致します。違いは、基板端からの距離を取るために J2 を 1.9 mm 下げたことと、シルク「Rx Tx V G」を J2 の上側 (基板端との間) に移したことです。
    - M5Stack の HY2.0-4P の色順 (黒 GND、赤 5V、黄、白) では、黄が STS_TX、白が STS_RX に当たります。PORT.C の公式ピン表は Core2 (黄 G14 = TXD2、白 G13 = RXD2)、Basic v2.7 (黄 G17 = TXD2、白 G16 = RXD2)、CoreS3 (黄 G17 = PC_TX、白 G18 = PC_RX) とも「黄 = ホストの TX、白 = ホストの RX」で、ストレートの Grove ケーブルなら合致します。
    - AtomS3R (PORT.CUSTOM、黄 G2、白 G1) のファームも TX = G2、RX = G1 で、PORT.C と同じ並びです。
- **JP1 (BAT–+5V のはんだジャンパ) を削除**: JP1 は B.Cu にある、隙間 0.3 mm のオープン型ジャンパです。JLCPCB はコネクタを裏面からウェーブはんだ付けするので、JP1 がはんだで短絡する恐れがあると考えました。短絡すると、サーボ電源 BAT が AtomS3R の 5 V に直結します。Unitree サーボでは BAT と +5V をつなぐ用途がないので、ジャンパごと削除しました。
  - 後で確認した JLCPCB の組立能力のページには、「はんだは注文した THT 部品にだけ付け、使わない穴ははんだから保護する」とあります。短絡の恐れは、ここで見積もったより小さかった可能性があります。それでも用途がないので、削除はそのままにしています。

| C131339 (PH 3P) | +180° | (+2.0, 0) mm |

`tools/jlcpcb_export.py` を KiCad 同梱の Python で実行すると、補正を入れた BOM (`bom_jlcpcb.csv`)、CPL (`cpl_jlcpcb.csv`)、ガーバーとドリルの zip を `production/` (git 管理外) に出力します。出力した CPL どおりに JLCPCB のランドパターンを置くと、パッド中心のずれは THT コネクタで 0 mm、SMD で 0.05〜0.21 mm でした。0603 などのずれは、KiCad のパッドが手はんだ用に長いためで、部品の中心は一致しています。発注時は、JLCPCB の配置プレビューで向きを確認してください。

**サーボ 5 ポート化と電源の強化 (外形 50 × 35 mm)**: サーボ用コネクタを 2 個から 5 個 (J3〜J7) に増やし、電源入力を JST XH (3 A) から XT30UPB (15 A) に変え、入力の直後に電解コンデンサ C7 を入れました。外形は横幅 50 mm のまま縦を 35 mm に伸ばし、取り付け穴は四隅から 5 mm (40 × 25 mm 間隔、上の 2 個は従来と同じ位置) にしました。

- **サーボ用コネクタ (2026-10-12 に変更)**: DYNAMIXEL 版から引き継いだ JST EH (2.5 mm ピッチ) のままでしたが、Unitree J288/S288 のサーボ側は JST PH 2.0 で、付属品も PH 2.0 ケーブルです (取扱説明書の同梱品と端子定義)。J3〜J7 を JST PH の 3 ピン縦型 B3B-PH-K-S に替えました。
  - ピン番号はサーボ本体のヘッダに合わせ、1 = GND、2 = VCC (BAT)、3 = SIGNAL です。当初は取扱説明書の表 (① SIGNAL・② VCC・③ GND) を JST のピン番号と解釈して逆にしていましたが、サーボの外形図 (2026-10-12、ユーザ提供) で確認して直しました。外形図のヘッダは、ピン列が前面寄り、背面の壁にピン間のリブがあり、この向きから JST の 1 番ピンが「−」の位置に当たります。サーボどうしの数珠つなぎでは 1 番同士 (− 同士) をつなぐストレートケーブルが前提なので、基板も同じ番号にすれば付属ケーブルがそのまま使えます。回路図の J3〜J7 は上下反転せず、3 番 (signal) を上に描いています。
  - PH は 1 ピン 2 A で、J288 の最大 1.92 A に対してサーボ側のコネクタと同じ制約です。
  - KiCad の PH のパッド (1.2 mm 幅、穴 0.75 mm) はランド幅が 0.225 mm なので、プロジェクト内のコピーでパッド幅を 1.25 mm にしました (ランド幅 0.25 mm)。
  - 90° 回して 1 番 (GND) を下にし、上から信号・BAT・GND の列が 2.0 mm 間隔で並びます。ヘッダの前面 (ロック側) は左向きです。ポートの間隔は 6.0 mm (本体どうしの隙間 1.5 mm)、BAT と GND の直線配線は 2.3 mm 幅 (熱逃がしの輪 2.25 mm を覆う) にしました。
- **電流の想定**: J288 (Maximum Line Current 1.92 A) を 1 ポート 1 台、5 ポートで最悪 9.6 A です。PH コネクタは 1 ピン 2 A、XT30 は 15 A です。
- **C7 の役割**: 電源ケーブルのインダクタンスとサーボ内部のセラミックコンデンサが作る、挿入時の電圧の跳ね上がりと振動を抑えます。デイジーチェーンの遠い側の電圧降下 (配線抵抗による) は直りません。J288 は最大 25.2 V なので耐圧 50 V にしました。
- **配置**:
  - 上の列: J2 (Grove) と基板名のシルク。
  - 中段: 送信イネーブル回路と電源 (従来の 2 列配置)、その右に C7 と J1 (XT30)。J1 は右端に縦向きに置き、+ を上、− を下にしています。
  - 下の列: サーボポート J3〜J7 (JST PH) を 90° 回し、6.0 mm 間隔で一列に並べました。ピンが横 3 列に揃い、上から信号 (3 番ピン)、BAT (2 番ピン)、GND (1 番ピン) です。5 個は並列なので、シルク「Sig / BAT / GND」は J3 の左に 1 組だけ置いています。間隔は、このラベルを左下の取り付け穴のネジ座面 (Ø7 mm) の外に置き、J7 を右下の穴から離せる最大値です。
- **BAT と GND の銅箔**:
  - 信号: 表面で、R2 から真下の J5 へ下ろし、3 番ピンの列を一直線に結んでいます。
  - BAT: 裏面のベタ (優先度 1 のゾーン) です。J1 の + ピンから右端を下り、ポートの列の下の帯へ広がります。さらに 2 番ピンの列を幅 2.3 mm の裏面の配線で一直線に結んでいます。配線は両端のポートの外側まで延ばし、5 個とも同じつながり方 (熱逃がしの隙間なし) にしました。J1 のピンだけ、ゾーンに全面で接続しています。
  - GND: 表面のベタが BAT のベタの上に重なり、電流の戻り道になります。1 番ピンの列も幅 2.3 mm の表面の配線で一直線に結んでいます。配線幅は、ピンの熱逃がしの輪 (列方向の外径 2.25 mm) を完全に覆う値です (EH のときは輪 2.7 mm に対して 2.5 mm で、幅 0.1 mm の切れ込みが残っていたので 2.8 mm にしていました)。
  - BAT のベタの外周は GND のベタの外周に揃え、細い GND の銅箔が残らないようにしました。
  - BAT のベタの入り隅 (右端から下の帯へ曲がる角と、右下の取り付け穴の切り欠き) は 45° で面取りし、電流が 90° の角に集中しないようにしました。配線の 90° の角も、ビアやパッドの中を除いて 45° で面取りしています。
- **取り付けネジと BAT**: 裏面にネジ頭、ワッシャ、金属スペーサが座っても BAT に触れないよう、4 つの取り付け穴の中心から半径 3.5 mm (Ø7 mm) の範囲に BAT の銅箔を置いていません。BAT のベタは穴の中心から 3.75 mm 以上離れています。右下の穴の周りは裏面の銅箔がなく、ほかの 3 つの穴の周りは GND です。範囲内の銅箔はスクリプトで調べ、どの穴も GND 以外の銅箔がないことを確認しました。
- **基板端からの距離**: JLCPCB の組立規約は「部品本体と基板端の距離は 2.5 mm 以上」で、組立能力のページでは Economic PCBA のエッジレールは「Not necessary」です。今回は全部品の本体を基板端から約 3.0 mm 以上離しました (J2 が 2.97 mm、サーボポートが 3.06 mm)。距離は KiCad のフットプリントの F.Fab (部品外形、ピン 1 の目印の線を含む) で測っています。
- **U2 のフットプリント**: DYNAMIXEL 版から引き継いだ U2 (SOT-23) は KiCad 6/7 の頃の旧版で、DRC が「ライブラリと一致しない」と警告していました。パッドは同じで、シルク (ピン 1 の三角マークがない)、コートヤード、3D モデルのパスが古いだけでした。KiCad 9 のライブラリ版に差し替えています。
- **JLCPCB の製造ルール (2026-10-12)**: 基板の設計ルールは DYNAMIXEL 版の緩い値 (基板端の銅のクリアランス 0.025 mm など) のままで、DRC が J2 のランド幅とシルクの文字の小ささを検出できていませんでした。JLCPCB の 2 層・1 oz の推奨値をプロジェクトの DRC ルールファイル (`.kicad_dru`) とボード設定に入れました。
  - スルーホールのランド幅 0.25 mm 以上、ビアは 0.075 mm 以上
  - 配線幅と間隔 0.15 mm 以上、穴と穴 0.45 mm 以上、銅と基板端 0.3 mm 以上
  - シルクの文字は高さ 1.0 mm・線幅 0.15 mm 以上、パッドとシルク 0.15 mm 以上
  - シルクの線: KiCad 標準ライブラリは 0.12 mm で描いているので、線幅だけ 0.15 mm にしたコピーをプロジェクト内のライブラリに置き、全部品をそれに差し替えました (回路図のフットプリント欄も `Library:` に変更)。基板上の文字はすべて高さ 1.0 mm・線幅 0.15 mm です (J2 とポートのラベルは文字幅 0.8 mm)。
  - 文字が大きくなったので、IC の部品番号を本体の外へ移し、TP1 を 1 mm 左へ移しました。
- **結果**: JLCPCB の推奨値のルールで、DRC は警告も含めて 0 件、未配線 0 です。CPL は 23 部品すべてを JLCPCB のランドパターンと照合しました。パッド中心のずれは THT (90° 回したサーボポートを含む) で 0 mm、SMD で 0.03〜0.21 mm です。
- **J1 の 3D モデル**: KiCad 9 に XT30UPB の 3D モデルがないので、J2 と同じく EasyEDA の STEP (C428721) を使っています。フットプリントはプロジェクト内のライブラリにコピーしたもので、モデルのオフセットを (+2.5, 0, 0) mm にしています。
- **ビアとベタ (2026-10-12)**:
  - GND ビアの銅が他ネットの配線のクリアランス (0.5 mm) に入り、ベタの縁に出っ張りを作っていました。C6・U4 のビアと、裏面の +3.3V・RX の配線をずらしました。
  - JLCPCB のクリアランス 0.15 mm のルールが、ゾーンのクリアランスも上書きしていました (KiCad で塗り直すと 0.15 mm になる)。ゾーン用の 0.5 mm のルールを `.kicad_dru` に足しました。
- **ヒューズ F1 (2026-10-12、作業ブランチ `feat/fuse`)**: J1 の + と BAT の間に、ミニ平型ヒューズ (32 V、ユーザが差す。J288 × 5 台で 15 A) を入れた。ホルダーは XFCN XF-508P-B-B (C19727305、絶縁ブロック付き。最初の Keystone 3557 のクリップ 2 個 C2680614 は JLCPCB の発注画面で在庫 0 だったので替えた)。F1 は J1 の左 (元の C7 の場所) に縦に置き、C7 は上側へ移した。詳細は基板リポジトリの `docs/design.md`。
- **基板リポジトリの文書 (2026-10-12)**: 決めたことと理由、レビューでの指摘と対応は `docs/design.md` に、作業のルールと検査のコマンドは `AGENTS.md` にまとめました。

### 7.1 試作基板の検証結果 (2026-10-21)

JLCPCB で実装した試作基板 (外形 50 × 35 mm、R4 = 470 Ω、発注は基板リポジトリの 062722a) を、AtomS3R と Grove でつないで確かめました。サーボの電源は 7.5 V 3 A の AC アダプタ、温度は室温です。サーボ 5 台での確認はまだです。

**直流の確認** (`bench` の `HOLD` と `LEVELS`、S288 接続)

| TX | RX (プルアップ) | RX (プルダウン) | 意味 |
|---|---|---|---|
| High | High | High | U4 がバスの High を出している (受信) |
| Low | High | Low | U4 が出力を止めている (TXEN が出ている) |

**ベンチ** (サーボと J1 の電源を外し、G5 を J3 の 3 番ピンへ。TXEN は G5 を TP1 へ)

| 試験 | 結果 | 合格基準 (§7) | 判定 |
|---|---|---|---|
| `bench.py check` | アイドルで TX・RX・バスとも High。20 µs の Low がバスに 19,988 ns で出る。RX (プルダウン) は 23.61〜23.64 µs Low | RX が TXEN 中は Low、アイドルで High | 合格 |
| `bench.py sweep` (W = 162.5 ns〜2.25 µs) | 長いアイドル後の S = 12.5 ns (1 刻み)。間隔 4 µs まで保持 (不足 0)、6 µs で解放 | S ≤ 20 ns、3.2 µs まで保持、7.5 µs 以内に解放 | 合格 |
| `bench.py packet`、4 Mbps | 3 種類とも 8/8 で復号。S = 12 ns、理想受信器の余裕は最小 112 ns (完全なら 125 ns)。再イネーブル 0 回 | 復号 OK、再イネーブル 0 回 | 合格 |
| `bench.py packet`、6 Mbps (参考) | 3 種類とも 8/8 で復号。S = 13〜14 ns、余裕は最小 63 ns (完全なら 83 ns) | — | — |
| `txen.py hold` | Low パルス 1 本のあとの保持: W = 250 ns で 5.49〜5.61 µs、1 µs で 5.58〜5.66 µs、9 µs で 5.83〜5.85 µs | §6.3: 3.27〜7.30 µs (典型 5.2 µs) | 合格 |
| `txen.py gap` | 間隔 5.0 µs まで保持、5.6 µs で 8/16 解放、6.0 µs で 16/16 解放 | 同上 | 合格 |
| `txen.py packet`、4 Mbps | 停止とストレス (0xFF を含む) の両方で 16/16 が TXEN の High 1 本。最後の立上りから 5.39〜5.58 µs で解放 | パケット中に解放しない | 合格 |

- **S**: 現行基板 (50 / 88 ns) から 12.5 ns になり、§6.3 の見積り (典型 5〜10 ns、最悪 16 ns) とほぼ合います。測定の分解能は 12.5 ns です。
- **保持時間**: 実測 5.4〜5.9 µs は、設計の典型 5.2 µs よりやや長く、範囲 (3.27〜7.30 µs) の中ほどです。パケット中の最長の High (2.25 µs) に対して 2.4 倍、応答開始 (最後の立上りから約 21 µs) まで 15 µs 以上の余裕があります。Low が長いほど保持がわずかに長いのは、D1 の電流が減って RC の始まりの電圧 V0 が下がるためと考えられます (§6.3 の V0 = 0〜0.3 V の範囲)。
- **6 Mbps の「再イネーブル」表示**: `bench.py packet` は 6 Mbps で「直前の High 1 ビットで再イネーブル」と表示しましたが、解析の誤検出です。80 MHz / 13.3125 の分数分周でエッジが 12.5 ns 揺れ、S の半分 (約 6 ns) のしきい値を超えるためです。1 ビット (166 ns) の High で TXEN が切れることはなく、`txen.py` でも保持は 5 µs 以上です。4 Mbps (整数分周) では表示されません。

**S288 (4 Mbps 設定)**

| 試験 | 結果 | 合格基準 (§7) | 判定 |
|---|---|---|---|
| `bench.py servo -n 100000`、停止 / ランダム | どちらも 100,000 / 100,000、誤り 0 | 誤り 0 | 合格 |
| `bench.py margin`、停止 / ランダム | どちらも −3.03〜+0.31% が 100%。+0.63% で 98〜99.7%、+0.95% で 98.7〜99%、+1.27% で 0.7% | 公式アダプタ (−2.44〜+0.63%) を含む | 上側が 0.3% 足りない |
| `first_edge.py delta` | D = −2〜+8 (−25〜+100 ns) で 100%、+112.5 ns で 72% | D = −1〜+5 で 100% | 合格 |
| 同上、DE 解放 → 応答開始 | 15.1〜18.5 µs (中央値 15.4〜15.6 µs) | (記録) | — |
| `sin_swing`、4,000,000 bps、10 s + 60 s | 14,000 周期で無応答 0、受信エラー 0。位置のずれ ±0.007 rad 以内 | 取りこぼし < 0.01% | 合格 (下記) |

- **データ依存の消失**: 停止とランダムで受信窓がまったく同じです。現行基板・午前の「ランダムでは −1.23% のみ」(§3.2) から、パケット途中の再イネーブルがなくなったことが確かめられました。
- **4 Mbps ちょうどで動く**: 現行基板は 4 Mbps の `sin_swing` で約 51% を取りこぼし、3.95 Mbps にずらす回避策が必要でした (§8)。新基板では回避策が要りません。
- **窓の位置**: 幅は 3.34% で公式アダプタ (3.07%) より広いものの、全体が遅い側へ約 0.45% ずれています。9.5 ビット × 250 ns に換算すると、先頭の遅れが公式アダプタより約 10 ns 大きいことに相当します (計算値)。§6.3 の見積り (典型 5〜10 ns、最悪 16 ns) の範囲です。`first_edge.py delta` でも、先頭の Low をさらに 25 ns 短くするまで 100% なので、先頭の遅れの余裕は 25 ns 以上あります。
- **取りこぼしの率**: 誤り 0 回からの 95% 上限 (3 ÷ 回数) は、`sin_swing` の 14,000 周期だけで 0.021%、4 Mbps でのやり取り全体 (214,000 回) で 0.0014% です。
- **3.3 V と R_bleed** (§6.4): やり取り中の 3.3 V は 3.299〜3.300 V で、持ち上がっていません (テスター)。アイドル時の信号線は 4.13 V で、サーボ側のプルアップ先を 5.0 V とすると、プルアップは 10.05 kΩ × (5 − 4.13) ÷ (4.13 − 3.30) ≈ 10.5 kΩ (5 V が 4.9〜5.1 V なら 9.3〜11.7 kΩ) です (計算値)。U3 が High を出している間に流れ込む電流は 1 台で 0.16 mA、同じサーボ 5 台で 0.78 mA (計算値) で、R_bleed (470 Ω、7.0 mA) で十分です。2.2 kΩ (1.5 mA) でも足りる値ですが、J288 のプルアップは未測定なので 470 Ω のままにしています。
- **サーボの温度**: 試験の間に、サーボが報告する温度が 37 → 53 ℃ と上がりました (巻線は 31 → 37 ℃)。止まっているモード 0 の試験中も上がっていたので、サーボ自身の発熱です。MError は 0 のままでした。

**J288 (出荷時の 6 Mbps のまま)**

| 試験 | 結果 |
|---|---|
| 4 Mbps で `scan` | 応答なし (サーボの設定が 6 Mbps のため) |
| 6 Mbps (実際は 80 MHz / 13.3125 = 6,009,389 bps、+0.16%) で `bench.py servo -n 20000`、停止 / ランダム | どちらも 20,000 / 20,000、誤り 0 |
| 6 Mbps で `bench.py margin`、停止 / ランダム | どちらも −3.03〜+1.11% が 100% |
| 6 Mbps で `sin_swing` | 2,000 周期で無応答 0、受信エラー 0。**ただしサーボが動かない** (位置が変わらず、トルクは ±0.002 Nm 以下) |

- **6 Mbps について**: ESP32-S3 のデータシート (§4.2.1.1) では、UART は最大 5 Mbps です。6 Mbps は仕様の範囲外で、この個体・室温では誤りなく動いた、という結果です。基板は 4 Mbps だけを扱う方針のままです。
- **J288 が動かない件**: 同じファームウェアと同じ 7.5 V で S288 は動いたので、基板や通信ではなく J288 側の条件です。ユーザが公式ツールで J288 を 4 Mbps に設定し直したあとは、同じ 7.5 V で動きました (下表)。電源電圧は原因ではありません。6 Mbps の設定のせいか、公式ツールでの書き換え (再起動を含む) のせいかは切り分けていません。

| J288 を 4 Mbps に設定したあと | 結果 |
|---|---|
| `sin_swing`、4,000,000 bps、10 s | 2,000 周期で無応答 0、受信エラー 0。位置のずれ ±0.007 rad 以内 |
| `sin_swing`、4,000,000 bps、60 s | 12,000 周期で無応答 0、受信エラー 0。位置のずれ ±0.007 rad 以内。サーボの温度は 38 → 39 ℃ |
| `bench.py servo -n 100000`、停止 / ランダム | どちらも 100,000 / 100,000、誤り 0 |
| `bench.py margin`、停止 / ランダム | どちらも −3.03〜+0.31% が 100% (S288 と同じ)。速い側は +0.63% で 66〜68%、+0.95% で 29〜35%。遅い側は −3.32% で 95〜96%、−3.61% で 87〜89% |

- **個体差**: 誤り 0 の範囲は S288 と同じ −3.03〜+0.31% です。誤りが出始める境目は、J288 のほうが全体に約 0.3% 遅い側にあります (速い側は +0.63% で S288 98〜99.7%・J288 66〜68%、遅い側は −3.32% で S288 20〜23%・J288 95〜96%)。4 Mbps ちょうどでは、どちらも速い側に 0.31% 以上の余裕があります。

## 9. 未確認事項・リスク

1. ~~**サーボ側の信号電圧とプルアップ** (§6.4)~~: S288 は 5 V 系で、プルアップは約 10.5 kΩ (計算値)。R_bleed 470 Ω で 3.3 V は持ち上がらない (§7.1)。J288 は未測定。
2. **ベンチで測った S とサーボ接続時の S の差**: §4.2 の換算に 10〜20 ns の不確かさがあります。新基板では `first_edge.py delta` で先頭の遅れの余裕が 25 ns 以上あることを確かめました (§7.1)。ベンチでの S そのものは未測定です。
3. **ESP32-S3 の TX ピンの出力抵抗**: S の見積りの主な不確かさです。
4. **個体差**: S288 と J288 の 1 台ずつで、新基板での誤り 0 の範囲は同じ (−3.03〜+0.31%) でした (§7.1)。境目は J288 が約 0.3% 遅い側にあります。それ以上の台数は未確認です。
5. **ケーブルの長さと複数台の接続**: 今回はサーボ 1 台、短いケーブルでの結果です。バス容量が増えると、立上りと立下りが対称に遅くなります。U3 が能動駆動なので S への影響は小さいと見込んでいます。
6. ~~**J288 が 7.5 V で動かない**~~ (§7.1): 4 Mbps に設定し直したら 7.5 V で動いた。出荷時の 6 Mbps の状態で動かなかった理由は未確認 (この基板では 4 Mbps しか使わない)。
7. ~~**新基板のベンチ測定**~~: 済み (§7.1)。TXEN の保持は 5.4〜5.9 µs、S は 12.5 ns。
